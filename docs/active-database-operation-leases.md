# Active task and agent-chat database leases

Task generation and agent chat now hold their existing database registry token for the complete operation, including persistence of the provider response. Ordinary LRU pressure, including the scheduler's 30-second scan across more than 50 accounts, cannot retire these active handles. Nested holds are reference-counted and releases are idempotent. Every success, replay, preparation failure, provider error, cancellation, and persistence failure exits through a finally release.

The 50-entry cache limit is a soft limit while all candidate entries are actively held, loading, locked, or writing. Releasing an operation reruns ordinary eviction. There is no separate permanent pin/epoch map; operations already retain the database they use. This does not add global concurrency or capacity guarantees.

An explicit per-account/global cache clear remains a hard boundary: it permanently retires even held handles. A late agent response stays visible as an unconfirmed streamed response and cannot overwrite the replacement store. Task recovery takes the account lock, reacquires canonical storage, force-reads it, and updates only the exact still-running run ID. It never copies old source/result content, recreates missing tasks, alters a different run, or sends the provider request again. A durable not-sent checkpoint becomes failed; a sent/uncertain checkpoint becomes outcome_unknown and requires user review. If storage remains unavailable, the existing durable checkpoint conservatively prevents redispatch.

Regression coverage exercises actual task and chat services with synthetic transports/local protocol fixtures, ordinary scheduler pressure, exact-once history/usage/receipt preservation, subsequent work, explicit replacement/deletion/run changes, provider errors and cancellation, and lost admission acknowledgement. Registry tests cover nested holds, idempotent release, active overflow pruning, and hard invalidation while held. Real PostgreSQL coverage repeats scheduler eviction pressure with the existing isolated test database. No real model or user data is needed.
